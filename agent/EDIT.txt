MODEL EDIT PROTOCOL - follow these steps in order. Do not skip a step. Do not invent steps.

THREE RULES (most important)
R1. Never run "@PY@ mx.py apply" before the user says yes to the approval code of the LAST dry run.
R2. Never say something is done unless a command output shows it ("Checked: ...", "Saved ...").
R3. Write change files only in edits/. Never edit other files in this folder: they are regenerated.

STEP 1 - FIND THE NAMES
  Find the exact names of everything you will touch (case matters):
    @PY@ mx.py find <part of a name>          (or the find tool)
  Read the related files in modules/ when you need the current logic.
  To change or delete ONE existing step of a microflow/nanoflow, get the step ids first:
    @PY@ mx.py steps <Module.Flow>             (or the steps tool)
  To change an existing page or snippet, get its widget names first (names, [into] places, {Entity} of data views):
    @PY@ mx.py widgets <Module.Page>           (or the widgets tool)
  For a pluggable widget of the project (widgets/*.mpk: Data grid 2, filters, charts, ...), its property keys and values:
    @PY@ mx.py widgettype <name>               (or the widgettype tool; without a name: the installed widgets)
  To translate texts (titles, captions, labels, messages, enumeration and menu captions), list them with where [part]:
    @PY@ mx.py texts <Module or Module.Page> --missing tr_TR   (or the texts tool)

STEP 2 - WRITE THE CHANGE FILE
  Pick the operations (one line each), then read the fields of the ones you use:
    @PY@ mx.py ops                            (or the ops tool)
    @PY@ mx.py ops <name>                     e.g. @PY@ mx.py ops createPage
  Write edits/<short-name>.json. Use ONLY operations and fields from that output. Several operations in one file are
  fine; they run in order. Never delete a change file that worked: it is the record of what was applied.
  No operation fits: run @PY@ mx.py gap "<what the user wants>" (or the gap tool), then give the user the exact
  Studio Pro steps. Do not write a .js script unless this folder allows scripts (see SDK SCRIPTS).

STEP 3 - DRY RUN (writes nothing)
    @PY@ mx.py dryrun <short-name>            (or the dryrun tool)
  FASTEST: the plan tool does STEP 2 and STEP 3 in one call: give it the short name and the ops list; it saves
  edits/<short-name>.json and dry-runs it.
  If it prints ERROR: read the HINT line, fix the file, run again. After 5 failed tries: stop, show the user the
  last error and ask for help.
  If it prints EXPRESSION CHECK lines: fix the names in the change file and run again (Studio Pro would show errors).

STEP 4 - SHOW AND ASK
  Show the user, in this format:
    PLAN: <1-5 bullets: what changes and why>
    DRY RUN: <the numbered op lines and the "Changes:" lines from the output>
    ATTENTION: <every DATA LOSS line first, then every line under EXPRESSION CHECK / NOT STORED / OLD NAME STILL USED / STILL USED BY / Warnings,
               or "none">
    To apply: close Studio Pro and answer "yes <CODE>".
  Then STOP and wait for the answer.

STEP 5 - APPLY (only after the user said yes with that code; Studio Pro closed)
    @PY@ mx.py apply <CODE>
  It saves the model (with a backup), re-exports, shows the changed files and runs mx check when available.
  "does not match the last dry run" or "model changed since the dry run": go back to STEP 3, then STEP 4.

STEP 6 - REPORT
  Report from the apply output: the "Checked:" or "CHECK FAILED" line, the changed export files, the mx check result
  (or that it did not run). Fix OLD NAME / STILL USED lines with a new change (back to STEP 2).
  Tell the user: open the app in Studio Pro, look at the Errors pane, run the app, then commit as usual.
  Wrong result: ask the user to close Studio Pro, then run "@PY@ mx.py undo". It restores the model from before
  the apply. If undo says "The model changed after this apply", show the user the listed changes; use
  "@PY@ mx.py undo --force" only when the user says they may be lost.
  After an undo, fix the change file and run "@PY@ mx.py rerun <file>" (a gone file comes back from the backup).

ERRORS AND FIXES
- "not found in the model. Did you mean: X" -> use X (check with find).
- "unknown field 'a'. Did you mean: b" -> rename the field to b. No suggestion: the message or HINT lists the fields.
- "Module 'X' not found. Create it first" -> add { "op": "createModule", "name": "X" } as the first operation.
- "'X' needs its module: M.X?" -> write the full name M.X.
- "needs 'x'" -> add field x (see ops).
- "already exists" -> it is done already: remove that operation, or use another name.
- "no variable 'V' before this action" -> the variable must be a parameter or be created by an earlier action.
- "has N end events / outgoing flows" -> add "after": "<variable name created by a step>", a step id, or "start".
- "has no step with id" -> run @PY@ mx.py steps <Module.Flow> and copy the id in [brackets].
- "'x' cannot be changed on ..." -> the message lists the fields this kind of step accepts.
- "is only allowed inside a loop" / "unreachable" -> break/continue only in loops; nothing may follow end/break/continue.
- "unknown widget 'x'. Supported: ..." -> use a listed widget; other widgets: gap + Studio Pro steps.
- "no widget 'x' on Module.Page (widgets here: ...)" -> use a listed name (all: @PY@ mx.py widgets Module.Page).
- "shows or uses the object of dataView1" -> that widget can move only inside dataView1.
- "listenTo 'x' is no grid or list view on this page (...)" / "is ambiguous" -> use a name the message lists.
- "is not a language of this project ... add it first" -> put { "op": "addLanguage", "code": "<code>" } before it.
- "no translatable text at 'x'. Did you mean" -> copy the where [part] from @PY@ mx.py texts <Module.Document>.
- "datagrid2 ... is not possible here" -> use "kind": "classic" (or leave kind out).
- "needs an import mapping" / "export mapping" -> publishRest supports only simple parameters/results; do it in Studio Pro.
- "has no attribute 'A' (in $V/A). Did you mean: B" -> use B in that expression.
- "Studio Pro has this project open" -> ask the user to close Studio Pro, then run the same command again.
- "is a script. Scripts are off" -> use operations; if none fits: @PY@ mx.py gap "<what>" + Studio Pro steps.
- "Unknown command 'APPLY'" -> commands are lowercase.

SDK SCRIPTS (only in folders exported with --allow-scripts; otherwise mx.py refuses .js files)
  Write edits/<name>.js:
    module.exports = async ({ model, sdk, ops, log }) => {
      const entity = await ops.get("Sales.Order");          // any document or element by qualified name, loaded
      const a = sdk.domainmodels.Attribute.createIn(entity);
      a.name = "Weight";
      sdk.domainmodels.DecimalAttributeType.createInAttributeUnderType(a);
      await ops.addAttribute({ entity: "Sales.Order", name: "Code", type: "String(20)" });  // ops work here too
    };
  Before using a type, read its properties and create functions for this Mendix version:
    @PY@ mx.py api <Type> [parent word]       e.g. @PY@ mx.py api ObjectType MicroflowParameterObject
  Use only what is listed there. "NOT IN MENDIX <version>" lines fail and name the replacement
  (GridDatabaseSource -> GridXPathSource, DataView.editable -> editability). Follow the NOTE lines
  (listenTarget = a widget NAME, not an entity). Version errors in a dry run end with a HINT naming the fix.
  Microflow objects go in mf.objectCollection, flows in mf.flows (SequenceFlow origin/destination).
  The dry run reports NOT STORED values: fix the script until there are none.

THREE RULES (again)
R1. No apply without the user's yes for the code of the last dry run.
R2. No claim without command output that shows it.
R3. Change files only in edits/.
